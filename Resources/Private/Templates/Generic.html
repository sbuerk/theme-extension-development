The one template shared by every Extbase plugin registered through "ExtensionUtility::configurePlugin()", whatever CType it ends up as - "templateName = Generic" is a fixed string that method writes itself (".Build/vendor/typo3/cms-extbase/Classes/Utility/ExtensionUtility.php", read on both installed core versions), so a third-party extension cannot be handed a template of its own the way "tt_content.header"/ "tt_content.image" in "ContentElements.typoscript" are. That fixed string is also why this file sits at the *root* of "templateRootPath" rather than below "ContentElements/" alongside every other template here: a copy placed under "ContentElements/" was tried first and fails with "InvalidTemplateResourceException", found by running it. What differs per plugin is not the template but the TypoScript path: for a plugin registered as its own CType - every plugin on TYPO3 v14.3, only "PLUGIN_TYPE_CONTENT_ELEMENT" on v13.4 - "configurePlugin()" places its "EXTBASEPLUGIN" cObject at "tt_content..20", right beside "templateName", in the very same branch this template is rendered from - reproduced verbatim in "docs/architecture/content-elements.md". "{data.CType}" already carries that signature: it *is* the plugin signature for a plugin registered this way ("ExtensionUtility::registerPlugin()" adds it as the "CType" select item's own value, read alongside "configurePlugin()"), so the path below is built from it rather than fixed, and resolves to a different "20" per plugin without this template ever knowing which plugin it is rendering. Verified as an actual "f:cObject" call against a real plugin registration, not only by reading "CObjectViewHelper::render()" - it resolves the whole "typoscriptObjectPath" argument from the root of the merged setup array, not relative to the cObject this template is itself being rendered from, which is exactly why the path has to spell out "tt_content" and the CType rather than reading "20" alone. "tt_content.list" in "ContentElements.typoscript" is not a plugin's own branch, and it reuses this same template by this theme's choice rather than the core's: "list" is itself a CType, so "{data.CType}" resolves to "list" there, and the path below to "tt_content.list.20" instead. That node is a CASE keyed on "list_type" only because that section declares it one - no system extension does. The CASE is what turns the objects below "tt_content.list.20" into its branches - on v13.4 the ones "configurePlugin()" writes for a "list_type" plugin and the others named in the comment inside that CASE - and the record's "list_type" selects one, in place of a single "EXTBASEPLUGIN". "data" and "table" hand the content element to that cObject. Without them "CObjectViewHelper" starts a content object renderer with an empty record: the plugin then runs without its content element - no FlexForm settings, an empty record as "currentContentObject" on the Extbase request - and the "list_type" CASE of "tt_content.list" has no field to switch on.
