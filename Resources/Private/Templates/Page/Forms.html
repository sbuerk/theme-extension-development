The form showcase, rendered from the backend layout "forms" (Configuration/PageTsConfig/BackendLayouts/Forms.tsconfig). One realistic form, put together from the form contract of the component library (docs/development/component-library.md, "Forms") and nothing else: fieldsets, every control a request form reaches for, an input group on either side, choice groups inline and stacked, a switch, a hint on the fields that need one, and the same form a second time as a server would return it after a failed submission - the error summary linking to each invalid field, the invalid and the valid state - followed by the summary of a successful one. Where the styleguide's forms section shows the contract selector by selector, this shows it composed: whether the pieces work together in the order a form actually needs them, which no specimen asks. Like the styleguide it is literal markup, not driven by a record, and it ignores anything placed on the page: there is no "f:cObject" in this file, and the layout's only column is the inert colPos 999. A form content element was the alternative and was rejected: its output would not depend on its record at all, and it would be one more CType in the wizard, in the editor group's grants and in every list that holds the showcase complete, for a record with nothing to configure. THE FORMS SEND NOTHING, AND SAY SO Both forms carry method="dialog" and no "action". The submit buttons are real submit buttons, so pressing one runs the browser's own constraint validation - the required fields, the email and URL syntax, "minlength" - and ":user-invalid" repaints what fails. What follows validation is where the method comes in: a form whose method is "dialog" and that has no "dialog" ancestor ends the submission at that point, so nothing is sent and the page does not navigate. The reset button is a real reset. The page copy says the same to a reader, and "Tests/Acceptance/forms.spec.ts" holds the page to it. Ids carry the prefix "form-request-" in the first form and "form-returned-" in the second, so they cannot collide with each other or with the ids of the page chrome ("content", "nav-main", "theme-settings-panel"). Copy is literal English, for the reason given in docs/development/styleguide.md: it exists to be set in a typeface.

A request form of the kind a site built on this theme would carry, put together from the form components of the library alone.

Nothing on this page is sent anywhere. Pressing the submit button runs the browser's own validation, and a field that fails it is marked the way the second form below shows it. After that the form stops: its method is dialog, and a form with that method outside a dialog ends its submission once it is valid, without a request and without leaving the page. Every control is still a real one, the reset button included.
