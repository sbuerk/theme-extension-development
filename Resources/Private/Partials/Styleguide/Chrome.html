Styleguide section "chrome": the site header and the site footer in each of the arrangements their site settings can select. Contract: "layout/_site-header.scss", "layout/_site-footer.scss" and docs/development/component-library.md#layout. Literal markup, like every other specimen of this page - not the real partials. Those read "siteRootUrl", "mainMenu" and "languageMenu", none of which exists without a request, and the visual suite renders this partial with standalone Fluid and no TYPO3 at all. What is copied here is the markup the variant partials produce, which is what the contract in the stylesheet documents. --- Two things differ from the real chrome ------------------------------- Landmarks. A "header" element is the banner landmark only while it is not inside "article", "aside", "main", "nav" or "section" (HTML-AAM). Every specimen here sits inside the page's "main", so none of the four is a landmark and the page keeps the one banner the real site header is. That is also why none of them carries an "aria-label": the attribute is prohibited on the generic role these map to, and the heading above each specimen is what names it. The navigation inside each one IS a landmark, so each of those is labelled, and labelled differently. Widths. These headers are rendered inside the content column, not across the page, so what they show is the arrangement of their rows and not the widths the real header negotiates. Those are measured in a browser, at four viewport widths, by "Tests/Acceptance/frontend.spec.ts" on the page's own header, which is the default variant - the one whose single row has a budget to keep. Controls. Each specimen stands one icon button in for the controls slot, which in the real header holds the language dropdown and the display settings - two partials of their own, demonstrated in their own specimens. What the chrome section shows is the rows and slots they sit in. Measured, too. The instance renders one header variant per site, so these four headers are the only place a browser sees the other three. "the header panels in every header variant" in "Tests/Acceptance/frontend.spec.ts" finds them as the headers inside "#chrome", copies the page's own controls slot into the "__actions" of each, opens both panels and measures where they land, where the title sits and whether it reaches under a trigger. Removing a specimen, its "__actions" or the "chrome" id fails that test. "ComponentLibraryTest::theChromeSpecimensCarryEveryClassTheirPartialsWrite" holds these specimens to every class the chrome partials themselves write, so the arrangement cannot drift from them unnoticed. Every specimen link points at "#": these demonstrate markup and state.

Page chrome

The site header, in the four arrangements the site setting theme.header.variant selects. Each is a partial of its own below Partials/Page/Header/ and a modifier on .theme-site-header; the default carries no modifier at all, so a site that never touches the setting keeps exactly the header it had. The three others each give the title or the navigation a row of its own, which is why none of them has to re-negotiate the width budget the single row keeps.

The site footer follows below, in the two arrangements theme.footer.variant selects. Both chrome settings work the same way: a partial per value, a modifier per variant, a default that carries none, and a switch over literal partial names so the value of the setting never becomes part of a path.

Simple — the default

Title, navigation and controls in one row. The navigation is pushed to the end by margin-inline-start: auto, and the controls follow it in source order — no spacer element, and nothing to change when the controls slot is empty.

Centred

The title centred on a row of its own with the controls at the end of it, the navigation centred below. From the breakpoint up an empty counterweight at the start of the row takes as much space as the controls at its end, so the title is centred against the whole row rather than against the space they leave — centred in the remainder sits visibly off centre. Nothing in the row is positioned, so the panels of the controls drop under the whole header.

With actions

A call to action beside the controls, and the navigation on a row of its own. Both the target and the text of the call to action are site settings, and the target is a page uid rather than a link, so an integrator editing the setting cannot put a scheme into that href — the type is int and the core validates it. The TypoScript constant of the same name is free text, as every constant is, so this narrows the form and not the file. Either setting left at its default renders no call to action at all, and the variant is then simply a two-row header.

Two tier

A tinted meta row carrying the controls, with the title and the navigation in the row below. The meta row is a div, not a second landmark: it holds two controls that name themselves, and a landmark with nothing to say is noise in a screen reader's landmark list.

Footer — columns

The four content columns above the meta row, each slid down from the site root so every page shows the same footer. A column is where a row of platform logos goes: the last one below is a theme_sociallinks element, which is all the theme ships for that — a footer slot of its own would be a second name for a column.

Footer — newsletter

The same footer with a band above it. The band is a heading, an optional line and a button leading to the page that carries the actual subscription form — not a form itself: the theme has nowhere to post an address to, and a field that looks like a subscription and drops what is typed into it is worse than no field. Heading, page and label are all required, and the band is not rendered without any one of them.

The band's heading is an <h2> in the real partial, where the footer carries no other heading to nest under. Here it is an <h4>: this specimen sits under the <h3> above it, and an <h2> would claim the band is a sibling of the section.
