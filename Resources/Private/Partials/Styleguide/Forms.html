Styleguide section D1 - "forms". The specimens are literal markup copied from the markup contract the three "Resources/Private/Scss/forms/" files share in their header comments; nothing here is driven by a record, a "f:cObject" call or a data processor. Every form on this page carries "method=dialog" and every button is "type=button". A form whose method is "dialog" and which has no ancestor "dialog" element aborts submission in the HTML form-submission algorithm, and a "type=button" button never submits in the first place - so the two together mean neither a click nor implicit submission can navigate away from the styleguide. There is deliberately no "action" attribute either, which alone would only mean "submit to this URL". Ids are all prefixed "sg-form-" so they cannot collide with the ids the real page chrome occupies ("content" in "Layouts/Default.html", "nav-main" in "Partials/Navigation/Main.html", "theme-appearance-label" and "theme-palette-label" in "Partials/Page/AppearanceSwitcher.html"). Forms

The three files under Resources/Private/Scss/forms/ style one contract between them: _controls.scss the native controls, _field.scss the label, hint, required marker and vertical rhythm, and _validation.scss the error and success repaint of both. No content element in this extension renders a form, so this section is the only place the contract is exercised at all.

The field wrapper

.theme-field is a grid whose row order is source order: label, control, error, hint. Nothing reorders it, so the visual order and the reading order that the aria-describedby list assumes stay the same order. The asterisk in the label is a sighted-user affordance and carries aria-hidden="true"; what a screen reader announces is the control's own required attribute. .theme-field--inline puts label and control side by side for a field that reads as a short row, and the hint still spans the full width underneath.

The hint is described text, not a label. It sits last in the source and last in the reading order.

Between 5 and 100.

One class for every input type that resolves to the same box

.theme-input is the single class applied regardless of type. Text, email, url, tel, number, password, search and the whole date and time family resolve to the same box once border, background, padding and font are normalised, so none of them needs a selector of its own. The picker indicator of the date and time controls tracks the palette by itself: :root is given color-scheme: light dark in abstracts/_tokens.scss, and that is what the native icon reads — flip the appearance switcher in the header and the picker glyphs follow without a rule touching them.

The three types that get an override of their own

color, range and file render a fundamentally different user-agent widget, so each gets an explicit [type='…'] rule. The colour swatch loses the inset border the browser draws inside it, the range switches the shared border and background off because a range is a track and not a box, and the file control themes its ::file-selector-button with the secondary accent — the primary fill stays reserved for the form's own submit action, so a file picker next to it does not compete for attention it has not earned. The bare output element next to the range is styled without a class, the way hr and small are.

Current value: 7

Select, multiple select and textarea

The select keeps the native arrow: replacing it needs an icon asset and this library ships none, so only the box around the indicator is themed. optgroup is set in the secondary text colour and bold rather than the browser's italic. A select[multiple] is made tall enough to show a handful of options at once, so it is not mistaken for a single-row text field. The textarea resizes vertically only — horizontal resize would break the field grid it sits in.

Hold the platform's modifier key to select more than one entry.

Fieldset, checkbox and radio

Checkbox and radio keep their native widget and are coloured with accent-color; the library does not hide the input and draw a replacement, because that pattern exists mainly for browsers this design does not have to support. The checked state therefore needs no rule of its own. The indeterminate state does have one, in the secondary text colour rather than the primary accent, because it is a third state and not a variant of checked — it cannot be shown here, since indeterminate is an IDL property with no HTML attribute behind it and this page carries no script.

Validation states

.theme-field--invalid and .theme-field--valid are the explicit counterparts of :user-invalid — deliberately not :invalid, which matches the moment a field fails constraint validation, and for a required field that is the moment the form loads. Every empty required field would paint itself red before the reader had typed a single character. :user-invalid only matches once the browser considers the field dirty, after a blur or a submit attempt, and the two modifier classes stay available for a form that drives its own server-side or asynchronous validation instead of the native one.

No rule signals a state by colour alone. An invalid border also gets thicker, and the error message is prefixed with a warning glyph that is real content rather than a decorative background image, so both survive greyscale printing and a colour vision deficiency.

Disabled and read-only

Read-only is not disabled. A read-only value is still submitted and the control is still focusable and selectable, only editing is blocked, so it keeps full opacity and trades the editable background for the tint a disabled surface would use. Disabled uses opacity rather than a second background, matching .theme-button, so one rule reads as "inactive" everywhere in the library. select is excluded from the read-only rule because the attribute does not exist on it.

Status and dialog elements

progress, meter and dialog are styled in base/_elements.scss as bare elements, so they arrive through the rich text editor without a class and without anything to opt into. They belong to no component, which is why they sit at the end of the forms section rather than in one — they are native controls with no wrapper of their own.

progress takes its fill from accent-color. Chromium renders the track as a sub-element rather than as the element's own background, so the track colour is repeated in ::-webkit-progress-bar — without that the bar is unstyled there and correct everywhere else.

meter reports a measurement within a known range rather than progress towards completion. The browser picks its own fill colour from the value's position between low, high and optimum, which is why only the accent is set here.

dialog is shown with the open attribute, which is the only form the stylesheet can reach. A dialog opened with showModal() is promoted to the top layer, where stacking context and z-index no longer apply and ::backdrop takes over — the rule sets both so either route lands somewhere deliberate.
