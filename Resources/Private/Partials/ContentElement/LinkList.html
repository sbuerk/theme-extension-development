Shared list rendering for every content element that resolves its own "tx_theme_list_items" inline relation into a plain list of links - "theme_linklist", "theme_sociallinks" and the profile/contact links of "theme_author". Reuses ".theme-content-menu" (see "docs/development/component-library.md#content") rather than a component of its own: structurally this is exactly the same shape as the "menu_*" family already rendered through it - authored content in the content column, a flat list of links, no navigation-chrome semantics to drag in - so a purpose-built list component would only duplicate its list/link styling. " wrapper and its "aria-label" are the calling template's own, the same split "ContentElement/Menu" uses for "menu_*". Each item is one row of "tx_theme_list_item" as resolved by "TYPO3\CMS\Frontend\DataProcessing\DatabaseQueryProcessor" - see "Configuration/TypoScript/ContentElements.typoscript" for how the relation itself is queried. Every entry is "['data' => $row]", not the row itself - "DatabaseQueryProcessor" wraps each record that way so a nested "dataProcessing" has somewhere to add to (see the identical note in "Partials/ContentElement/../Templates/ContentElements/ MenuCategorizedContent.html", which reads the same processor's output). So the fields below are "item.data.link"/"item.data.link_label", never "item.link" - the latter resolves to nothing and would silently render no rows at all rather than failing. "link" is TCA type=link, rendered through "f:link.typolink", not as a plain "href": a TCA type=link value is stdWrap.typolink syntax - it may be a page, file, email or telephone reference exactly as the link wizard encoded it, not a bare URL string (".Build/vendor/typo3/cms-fluid/Classes/ViewHelpers/Link/ TypolinkViewHelper.php").
