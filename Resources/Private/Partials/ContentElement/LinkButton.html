The "theme_link" palette (tx_theme_link + tx_theme_link_label + tx_theme_link_variant + tx_theme_link_icon, Configuration/TCA/Overrides/tt_content.php), rendered as a ".theme-button" (Resources/Private/Scss/components/_button.scss). Shared by the three hero variants, theme_teaser and theme_media_teaser - theme_testimonial does not carry this palette at all, see its own template. "tx_theme_link" is a TCA type=link field. Its stored value is already a stdWrap.typolink parameter string (the page/file/url/email/record syntax TYPO3\CMS\Core\LinkHandling\LinkService writes), which is exactly what "f:link.typolink"'s "parameter" argument expects (.Build/vendor/typo3/cms-fluid/Classes/ViewHelpers/Link/TypolinkViewHelper.php, "$this->arguments['parameter']" fed straight into "TypoLinkCodecService"). That ViewHelper renders through "ContentObjectRenderer::typoLink()" rather than building a tag itself, which is also why it is explicitly named as an exception to TYPO3 v14's Fluid 5 change to null-handling on tag-based ViewHelpers (.Build/vendor/typo3/cms-core/Documentation/Changelog/14.0/ Breaking-108148-StrictTypesInFluidViewHelpers.rst: "f:link.*>, except for , which uses TypoScript internally") - behaviour verified identical on v13.4 and v14.3, nothing here needs a version split. "tx_theme_link_variant" - "Link style" in the form - only ever holds '', 'secondary', 'ghost' or 'link', read from the "items" of the column, not assumed. The switch covers exactly those values, one per modifier "_button.scss" ships; the empty default case renders the plain ".theme-button". "ThemeLinkRenderingTest" holds the items and the cases to each other. "tx_theme_link_icon" is an icon of the shipped set an editor picked, and goes before the label: it says what the link leads to, and leaves the end of the link to what says how it opens. It is decoration, hidden from assistive technology; the label names the link. The button's "gap" spaces it, in reading order, so it also comes first in a right-to-left page.
