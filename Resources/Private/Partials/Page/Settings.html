The display settings, rendered from "Partials/Page/Header.html" into ".theme-site-header__actions" on every page template: one cog button that discloses appearance, palette and the content-element outline. Markup contract: docs/development/component-library.md, styled by "components/_settings.scss" (the switch by "forms/_controls.scss") and operated by "Resources/Public/JavaScript/theme.js" - do not add or rename a class or a "data-theme-*" attribute here without the matching change there. --- Hidden until the script marker ------------------------------------- The whole control is hidden until "data-js" appears on the root, the same gate "components/_nav-main.scss" uses for the navigation toggle: without the module script the cog discloses nothing and no choice applies, so showing it before that script has run would be a promise the page cannot keep. --- A disclosure holding native controls, not a menu -------------------- The trigger is a plain button with "aria-expanded" and "aria-controls", the panel holds two radio groups and a checkbox, each group a "fieldset" named by its "legend". There is deliberately no "role=menu": radios and a checkbox bring their own keyboard behaviour - Tab between the groups, the arrow keys within one - and their own announced state, which the ARIA menu pattern would have to rebuild by hand. The radios stay in the document under their styled labels (see the SCSS), so none of that is lost to the styling. --- Server defaults ------------------------------------------------------ "settings.appearance" is assigned in "Configuration/TypoScript/Appearance.typoscript" from the three constants that also render the html tag attributes. It is used twice here: - for the initially checked controls. That is the truth for a visitor with no stored choice; for everyone else the module script re-reads the attributes on the root - which the inline head script has already resolved - and checks the matching controls before the panel can be opened. - as the "data-theme-default-*" attributes, which is what "Reset" restores. Once a stored choice has replaced an attribute on the html tag, the server default is nowhere else in the document, and the script must not have to guess it. The script keys on "data-theme-setting", not on the "name"s - those only group the radios. --- More than one on a page ---------------------------------------------- The panel's id and the radio "name"s are derived from the optional argument "idPrefix", "theme-settings" when it is not given - which is how "Partials/Page/Header.html" renders it. A second instance on the same page (a specimen, a copy in the footer) passes its own prefix; with the same one, its "aria-controls" would point at the first panel and its radios would join the first instance's groups. The script binds every ".theme-settings" and keeps all of them in step with the root.
