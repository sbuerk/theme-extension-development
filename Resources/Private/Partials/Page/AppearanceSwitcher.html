The appearance/palette switcher, rendered from "Partials/Page/Header.html" into ".theme-site-header__actions" on every page template. Markup contract: docs/development/component-library.md, styled by "components/_appearance-switcher.scss" - do not add or rename a class here without a rule there. --- Hidden until the script marker ------------------------------------- The whole control is hidden until "data-js" appears on the root, the same gate "components/_nav-main.scss" uses for the navigation toggle: neither group does anything without the module script that owns "data-theme-appearance"/"data-theme-palette", so rendering the buttons visible before that script has run would be a control that does nothing - see the SCSS file for the rule and the longer reasoning. --- Server-rendered "aria-pressed" -------------------------------------- Both groups below hardcode "aria-pressed" to the server default - appearance "auto", palette "neutral", per the step 4 contract's TypoScript constants. That is accurate for a first-time visitor with no stored preference; it is stale for a returning visitor whose "localStorage" holds a different choice, and it is the module script (out of scope for this file) that corrects the attribute - together with "data-theme"/"data-palette" on the root - once it runs. Fluid has no access to "localStorage" at render time, so it cannot render anything closer to the truth than the server default. Two "role='group'" regions, each "aria-labelledby" pointing at its own label element rather than a shared one, so the two groups read independently to assistive technology. Every option button carries "data-theme-appearance" or "data-theme-palette" - the exact attributes the module script reads and writes - and clears the tap-target floor in the SCSS.
