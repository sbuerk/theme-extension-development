The language menu: one entry per language of the site. "{languageMenu}" comes from core "LanguageMenuProcessor" ("Configuration/TypoScript/Navigation.typoscript"). Only the keys that processor has documented since TYPO3 9.3 are read here - "languageId", "navigationTitle", "hreflang", "link", "active" and "available". The item carries more than that on both supported cores - "locale", "title", "twoLetterIsoCode", "direction", "flag" and "current" - and none of them is needed by a menu of links. --- "active", never "current" ------------------------------------------- The processor derives "current" from the item states "CUR"/"CURIFSUB", and "prepareMenuItemsForLanguageMenu()" never emits either - it marks the language being viewed "ACT". So "current" is always 0 in a language menu, and reading it would leave the menu with nothing marked at all. "active" is the one that says "this is the language you are reading". "aria-current='true'", not "page": the entry is not another page, it is this page in the language already being read. --- The unavailable state is rendered, not hidden ------------------------ A language the current page has no translation for comes out with "available = 0", and it stays in the menu as plain text rather than a link. Hiding it would tell a reader the site has fewer languages than it has; linking it would promise a translation that does not exist and land them on the fallback without a word. That flag is not something "fallbackType" can talk out of. The state is decided by whether "getPageOverlay()" returned a record of its own - the marker it is recognised by is "_PAGES_OVERLAY" on v12.4 and "_LOCALIZED_UID" on v13.4, the same test under two names - and "LanguageMenuProcessor" never sets "special.normalWhenNoLanguage", so for any language other than the default an empty overlay is "USERDEF1" - unavailable. A "fallbacks: [0]" does not change it either: "PageRepository::getPageOverlaysForLanguage()" filters the default language out of the overlay chain with "array_filter()", so the chain is empty and there is no overlay to find. Only a *non-zero* fallback language that really has the page translated makes an entry available. None of these three keys is computed in PHP on either supported core, and that was read rather than assumed. The processor assembles each item as a JSON string built by TypoScript, with "cObject" slots 91, 92 and 93 supplying "active", "current" and "available" and a link placeholder substituted afterwards by "replacePlaceholderInRenderedMenuItem()". The state configuration is what sets them - "USERDEF1" and "USERDEF2" write "0" into slot 93, and "USERDEF2" is derived from "ACT" so it keeps slot 91. "buildConfiguration()" and the slot table are unchanged between 12.4.45 and 13.4.35. The class around them is not: v13.4 declares property types, takes its collaborators by constructor injection, drops "$menuTargetVariableName" and reads the request attributes where v12.4 reads "$GLOBALS['TSFE']" - none of which reaches these three keys. Neither core sets "special.normalWhenNoLanguage". So this template depends on the contract rather than on the mechanism, which is why one template serves both. The entry is a "span" rather than a link, so there is nothing to click and nothing in the tab sequence - a span is not focusable to begin with, which is why it carries no "hidden" and no "tabindex". "aria-disabled" is on it as a statement of state, not as a promise of an announcement: "aria-disabled" is only mapped to a disabled state on elements that can be disabled, and a bare "span" is not one, so a screen reader is not obliged to read anything out for it. What carries the meaning for every reader is that the entry is plain text next to entries that are links. The attribute stays because it is correct and costs nothing, not because it does the work. "lang" and "hreflang" carry the language of the entry, so "Deutsch" is announced in German whichever language the page around it is in. The guard below is emptiness only. Whether a menu of one language is worth showing is the caller's decision, and "Partials/Page/Header.html" makes it by counting - see the comment there. The landmark is "Languages", the dropdown trigger around it "Language": the trigger names the control a reader operates, the landmark names the list it contains. Both read "Language" once, which meant a screen reader announced the button and then the region with the same word twice over.
